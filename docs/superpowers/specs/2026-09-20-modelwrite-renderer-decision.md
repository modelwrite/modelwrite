# Decision: do we build our own renderer, or adopt one?

**Status:** decided. Short answer: we build the mapping, we borrow the algorithms, and we EXPORT to other renderers rather than adopting them.

## What "our own renderer" actually means here

We render **three views** from OKF into deterministic SVG:
1. **Structure** - a layered view of the whole model (containment and dependency edges).
2. **Process** - an activity flow laid out left-to-right, with parallel branches.
3. **Composition** - a platform model's subsystems and the process across them.

That is a **deliberate subset**, not a SysML tool. We do NOT render state machines, sequence diagrams, parametric diagrams, internal block diagrams or use-case diagrams. Saying that plainly matters more than the size of the code.

## Why NOT Mermaid or D2 as the renderer

Both are good tools. Four reasons, in order of weight:

**1. The picture must be a FUNCTION OF THE MODEL, and they take TEXT.**
Mermaid and D2 are fed a textual diagram description. To use them we would have to convert the model into that text first - introducing a **second representation of the model**, generated by us, which the picture is then drawn from. That derived text can drift from the model, and nothing in either tool would notice. This project has spent its whole life catching things that look authoritative and are not; a diagram drawn from a derived description rather than from the model is that defect with a picture attached.

**2. DETERMINISM IS A TESTED PROPERTY HERE.**
The same revision must render byte-identically, because the artefact is evidence: it goes in a review pack, it is compared between revisions, and the fidelity gate hashes what it produces. Mermaid renders in a browser at view time - the same source can differ across versions, and its layout is not specified as stable. An artefact that changes when you look at it again is not evidence.

**3. THE IDS ARE THE INTERFACE.**
Every node in our SVG carries `data-mw-id` bound to the model's element ids. That is what makes click-to-select, `?select=` deep links, tree/panel synchronisation, and cross-references between views work. A third-party renderer assigns its own identities, and the link back to the model becomes a name-matching exercise.

**4. COMPLETENESS IS A TESTED PROPERTY.**
"Every node and every edge is drawn" is one of our tests - including the nodes no edge reaches, which an earlier version silently dropped. Renderers optimise for readable output and will legitimately collapse, cluster or omit. For a picture that claims to BE the model, that is a correctness bug, not a style choice.

Secondary: Mermaid is a large JavaScript bundle and D2 is a separate compiled binary. Both cut against an air-gapped deployment that fetches nothing and builds nothing at runtime.

## What we SHOULD borrow

- **Algorithms: yes.** Layout is a solved problem and a licence-clean crate beats a hand-rolled one. We evaluated `rust-sugiyama` (MIT), `gen-sugiyama` (MIT) and `layout-rs` (MIT) for exactly this. We currently ship a hand-rolled deterministic layered layout because **determinism was the binding constraint** and it is tested; the crates stay documented as the replacement, behind a thin module boundary so swapping is a one-file change.
- **Notation conventions: yes.** Shapes and stereotype keywords are a standard, not an invention. Our activity nodes are rounded rectangles and requirement nodes are document shapes because that is what an engineer already reads.
- **Icon sets: yes, with licences recorded.** MIT/ISC/Apache-2.0 sets only, embedded in the binary. An operator supplies brand-shaped symbols as an icon pack, because trademarked marks cannot ship in an open-source repository.

## The move that resolves the tension: EXPORT, DON'T ADOPT

Offer **export to other notations** instead of rendering through them. A Mermaid or D2 text export uses the existing **binding** frame - the same one built for legacy XMI:

- a **loss report** saying exactly what the target notation cannot express (`lossy`, `unmappable`, each with a subject and a reason);
- **nothing mapped silently**;
- the ability to take a model into somebody else's tooling without that tooling becoming the source of truth.

That gives a user the whole ecosystem of renderers, keeps this platform's claim ("the picture equals the model") intact for the pictures WE make, and reuses machinery that already exists and is already tested. An organisation gets both: our provable diagrams for evidence, and Mermaid/D2 text for everything else.

## The decision rule, stated once

**Adopt a library when it computes something we can verify. Do not adopt one when it owns the mapping from model to picture** - because that mapping is the thing this platform promises is faithful.

# Appendix: the `rust-sugiyama` evaluation, and its outcome

**Outcome: evaluated, licence-clean, 1.75-buildable, and REJECTED for this workload. The hand-rolled deterministic layout stays.**

## What was measured

- **Licence:** MIT. Compatible.
- **MSRV:** `cargo +1.75.0 build -p mw-graph` succeeded with the crate added - **but only because the workspace already pins `indexmap = =2.11.4`**, which unifies the crate's transitive `indexmap` requirement. In a bare crate without that pin it resolves `indexmap 2.14.2` (edition 2024) and fails at 1.75. The engine floor is preserved by an existing pin, not by the crate.
- **Determinism:** identical output across four processes and three in-process runs on the corpus. **But the crate's own source states that "order of elements in a row cannot be guaranteed"** - a hash-iteration dependency. Determinism here is **observed, not contractual**.

## Why it was rejected

The crate is a **generic** Sugiyama layout with no SysML awareness. On this project's real corpus:

- the 33 child-to-parent association edges cycle against the part tree and would be **collapsed as cycles**;
- there is no **containment weighting**, so parents drift from their children;
- there is no **process** view, which is a first-class diagram here;
- it returns grid units rather than pixel extents for node sizing, plus a list of disjoint subgraphs the caller must merge;
- it **panics on the corpus's two dangling edges** - and dangling edges are exactly the case this platform must REPORT rather than crash on.

Adopting it would mean re-implementing edge semantics, containment weighting, the process layout, node sizing and dangling handling **on top of it** - more work than the implementation it would replace.

## The decision rule, applied

*Adopt a library when it computes something we can verify.* A layout is verifiable, so the crate deserved the trial - and the trial produced the answer. What we need is not "a Sugiyama layout" but **"a deterministic, SysML-aware arrangement of THIS model's nodes"**, and that includes semantics the crate does not have.

Two properties settled it:

1. **DETERMINISM BY CONSTRUCTION beats determinism by observation.** The committed layout sorts every iteration and breaks ties by node id, and is unit-tested for byte-identical output. A library that is *usually* stable is not the same artefact as one that cannot vary.
2. **DANGLING EDGES ARE A REPORTED CASE, NOT A PANIC.** The platform exists to name what does not resolve; a layout engine that panics on the corpus's two dangling edges contradicts the product.

The implementation stays behind the one-file module boundary (`engine/graph/src/layout.rs`), so if a future crate is deterministic by contract and SysML-aware, switching remains a single-file change.
