What it is

Modelwrite is an open-source platform for model-based systems engineering (MBSE) that an organisation runs on its own infrastructure. It stores systems models in OKF — the Open Knowledge Format, a single self-describing JSON document — and it proves, with a recorded gate run, that a change or a migration lost nothing.

The identity of the project is the model you can prove. A claim is either checkable, or it is labelled as unchecked. Every statement about fidelity, model health, or change traces to a recorded, deterministic gate run.

Why it exists

Legacy MBSE tools such as CATIA Magic are costly to licence and hard to use, and there are not enough engineers who can drive them. Modelwrite exists so an organisation can move off those tools — migrating its models with measured fidelity — and so that AI agents can help with the skilled repetition of building and reviewing models, while a human makes every commit. Agents draft; the gate and the human check.

Install and run

The Rust crates are not published to crates.io — both declare publish = false in their manifests — so cargo install will not work. Build from this repository.

The crates build and run from source. The service is mw-server; the CLI is mw-cli, which builds the mw binary:

cargo build --workspace
cargo run -p mw-server

The container image builds from deploy/Dockerfile (see deploy/README.md):

docker build -f deploy/Dockerfile -t modelwrite/modelwrite:0.1.0 .

To try the full stack on one machine, from the repository root:

docker compose -f deploy/docker-compose.yml up --build

The server runs in open mode (anonymous admin) unless a token or JWKS is configured. The container refuses to start open on a reachable interface unless MW_ALLOW_OPEN=yes is set.

What works

CapabilityStatusWhat it means
Commit model Works Content-addressed blobs, a deterministic commit hash, section-scoped diffs, three-way merge with a real least-common-ancestor, element locks as leases, an append-only audit log written inside the mutation transaction, identity and roles.
Round-trip gate Works Zero element, edge, attribute or document-field loss; graph integration; optional strict coverage; deterministic evidence records.
Workbench Works Server-rendered HTML and inline SVG. No build step. Nothing fetched from the network at page load.
Interoperability Partial A binding contract, a SysML v1 XMI reader, and migration as a gated operation: the source artifact is retained content-addressed before anything else, fidelity is measured, and a lossy migration is refused until the specific loss is accepted by name.
Agent loop Partial A Reasoner trait, proposals a human reads, agent actions distinguishable in the audit log, and an enforced rule that an agent cannot write. A human with the write role accepts a proposal through an import-scoped route.
Governance Works Commit provenance (authored / imported / unknown), migration rules enforced at the commit path, and per-commit check records.
Analytics Works Portfolio compliance, cost joins with weakest-link confidence, and exact decimal money (scaled integers, no floating point).

What it does not do

  • An agent cannot write. It proposes; only a human with the write role accepts a proposal into a commit, and the resulting commit records both parties. An agent token cannot hold a write or admin role.
  • The agent loop is not wired end to end. Nothing outside engine/agent consumes the reasoner’s proposals, so a proposal does not reach the server on its own; a human drives the accept route. Acceptance is import-scoped: migration loss-report proposals only.
  • The first real vendor model has been tested — and the result is measured, not reassuring. The MagicDraw SysML model in sample/corpus/coffee-machine/legacy/CoffeeMachine-SysML-Model.mdzip (a 193 KB XMI in its com.nomagic.magicdraw.uml_model.model entry) contains 148 packagedElement and 57 ownedAttribute elements: 34 Blocks, 25 Requirements, and 28 traceability links (20 Satisfy, 3 Allocate, 4 Refine, 1 Verify). Importing it produces 34 structure elements (the Blocks), 25 requirements, 59 graph nodes and 28 graph edges — the Satisfy, Allocate, Refine and Verify links — alongside 270 content losses, every one Unmappable and named. Requirements and their traceability are now carried; Ports, Operations, Associations, visibility and other attributes are still reported as unmappable: named, never dropped in silence, but not carried. Reproduce it with cargo test -p mw-binding-xmi --test real_magicdraw -- --nocapture.
  • Real vendor migration is still not complete. The reader now carries requirements and their traceability — 25 requirements and 28 links (20 Satisfy, 3 Allocate, 4 Refine, 1 Verify), where the first measurement carried none — but it still loses 270 things: Ports, Operations, Associations, visibility and other attributes. Migrating a MagicDraw or CATIA Magic model without those losses is not yet supported.
  • The native XMI-to-OKF direction is not independently measured. The gate measures the binding’s own OKF-to-XMI-to-OKF round trip; the read rests on the binding’s self-reported loss report, not on an independent golden corpus.

The engine crates are the contract. The server, the CLI and every connector build on them; nothing bypasses the OKF crate and the gate.

Numbers you can check

  • 412 tests pass. Run cargo test --workspace --no-fail-fast from the repository root. 24 further tests — the PostgreSQL backend suite — are marked ignored in that run; the postgres CI job executes them against a real PostgreSQL 16 service container.
  • 4 CI jobs: engine, msrv, postgres, deploy — defined in .github/workflows/ci.yml.
  • Corpus (sample/corpus/coffee-machine), pinned by tests and the evidence annex: 99 graph nodes, 165 graph edges, 25 requirements, 49 blocks, 9 signals, 8 activities, 1 connected component, 0 isolated nodes.

Licence

The engine and server are AGPL-3.0-or-later. The OKF interchange format, and the importers and exporters, are Apache-2.0 — the split is project policy: “Importers and exporters ship under Apache-2.0; the engine stays AGPL-3.0-or-later” (CONTRIBUTING.md). The reference implementation of OKF lives in the AGPL engine.

Commercial use follows the documented open-core pattern: a private business repository alongside the public engine, an evidence annex, and rule packs.
